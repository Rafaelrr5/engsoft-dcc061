18enunciado completo da Lista 1

Considerando os modelos de processo de software clássicos e os métodos ágeis, em quais situações você utilizaria Casos de Uso e em quais Histórias de Usuário?

Resposta Gabarito do professor

Histórias de Usuários: sistemas desenvolvidos usando-se métodos ágeis. Por exemplo, um sistema financeiro, aplicativos web de delivery, transporte, e-commerce, etc…

Casos de Uso: sistema desenvolvido usando um método não-ágil e que possua alguns requisitos mais complexos e de difícil entendimento. Ou então quando o cliente exige que seja produzido antes um documento com os requisitos do sistema, para sua aprovação e antes de ter início o desenvolvimento. Por exemplo, um sistema para controle de armamentos das Forças Armadas (veja que se trata de um sistema mais sensível, para um cliente governamental e que possui uma estrutura hierárquica bastante rígida).

O que não pode faltar
  • Histórias de usuário: sistemas com métodos ágeis
  • Exemplos para histórias (financeiro, delivery, transporte, e-commerce)
  • Casos de uso: método não-ágil com requisitos complexos/difíceis
  • Casos de uso: cliente exige documento de requisitos aprovado antes
  • Exemplo para casos de uso (ex.: controle de armamentos, cliente governamental)
Matéria por trás da questão

U5 · Casos de uso

  • Caso de uso agrupa um conjunto de ações com objetivo bem definido, representando uma funcionalidade.
  • A especificação descreve as interações entre entidades externas e o sistema; valida se analista e usuário entenderam o mesmo; serve de base para os planos de teste.
  • Feita em linguagem natural — há diversos padrões estruturais, mas nenhum padronizado pela UML.
  • Estrutura típica: Número, Nome, Objetivo, Ator principal, Ator secundário, Fluxo principal, Fluxo alternativo, Restrições, Requisitos especiais.

U5 · Histórias de usuário — 3 C's e INVEST

  • Antes: analistas escreviam o PRD e repassavam aos programadores. Hoje: o PO senta junto dos devs e explica os requisitos.
  • 3 C's = Cartão + Conversas + Confirmação.
  • Cartão: lembrete para a conversa | Conversas: PO detalha durante o sprint | Confirmação: cenários/testes de aceitação usados pelo PO.
  • INVEST — boas histórias são: Independentes, abertas para Negociação, agregam Valor, Estimáveis, Sucintas e Testáveis.
  • Formato usual: 'Como <papel>, eu gostaria de <objetivo>'.

Dica: INVEST e 3 C's são siglas prontas para a prova.

Pergunta Mais provável
15enunciado completo da Lista 1

Diferencie requisitos funcionais de requisitos não-funcionais.

Resposta Gabarito do professor

Requisitos funcionais definem o que um sistema deve fazer; isto é, quais funcionalidades ou serviços ele deve implementar. Já os requisitos não-funcionais definem como um sistema deve operar, sob quais restrições e com qual qualidade de serviço. São exemplos de requisitos não-funcionais: desempenho, disponibilidade, tolerância a falhas, segurança, privacidade, interoperabilidade, capacidade, manutenibilidade, usabilidade, dentre outros.

O que não pode faltar
  • RF: o que o sistema deve fazer
  • RF: funcionalidades ou serviços a implementar
  • RNF: como o sistema deve operar
  • RNF: restrições e qualidade de serviço
  • Exemplos de RNF (desempenho, disponibilidade, segurança, usabilidade…)
Matéria por trás da questão

U5 · Funcionais vs Não Funcionais

  • REQUISITOS FUNCIONAIS: funcionalidades ou serviços que o sistema deve fornecer, de forma completa e consistente.
  • Ex.: 'O sistema deve permitir que cada professor realize o lançamento de notas das turmas nas quais lecionou'.
  • REQUISITOS NÃO FUNCIONAIS: não dizem respeito às funções específicas — confiabilidade, tempo de resposta, espaço em disco, restrições.
  • Ex.: 'O tempo de retorno das consultas não deve ser maior que 5 segundos'; 'deve ser compatível com Chrome e Firefox'.
  • Classificação dos RNF: de PRODUTO (usabilidade, confiabilidade, portabilidade, eficiência, desempenho, espaço), ORGANIZACIONAIS (entrega, implementação, padrões) e EXTERNOS (legais, éticos, privacidade, segurança, interoperabilidade).

Dica: Saber separar RF de RNF e citar as 3 categorias de RNF é item quase garantido.

U5 · Requisitos de Usuário vs do Sistema

  • DE USUÁRIO: destinados aos vários níveis da organização, de gestores a usuários.
  • Linguagem natural, tabelas, formulários e diagramas simples (casos de uso). Sem jargão de software ou notações formais.
  • DO SISTEMA: descrições mais detalhadas e de caráter mais técnico — versões expandidas dos requisitos de usuário.
  • Ponto de partida para o projeto do sistema; usam modelos como os diagramas da UML; podem integrar o contrato de implementação.
  • Ambos incluem requisitos funcionais e não funcionais.

Na prova antiga veio um cenário em itens: a) montar os times (PO, Scrum Master, devs); b) escrever histórias de uma biblioteca; c) o que vai no sprint backlog; d) para que serve a sprint review. Saiba os papéis, o que entra no backlog (9) e a diferença entre histórias do topo e do fundo (8).

Pergunta Mais provável
9enunciado completo da Lista 1

Além de histórias, quais outros itens podem fazer parte do backlog do produto?

Resposta Gabarito do professor

Quando se usa Scrum, histórias de usuários – ou seja, features ou requisitos funcionais do sistema – são o principal item do backlog do produto.

No entanto, outros itens também podem ser incluídos no backlog do produto, tais como:

  • Solicitações de correção de bugs, principalmente bugs importantes e que levarão mais tempo para serem corrigidos.
  • Manutenções adaptativas, como, por exemplo, migrar o sistema para uma versão mais nova de um framework, banco de dados ou linguagem de programação.
  • Refatorações grandes e importantes, bem como outras atividades para pagamento de Débito Técnico.
  • Instalação ou configuração de algum sistema ou framework mais complexo, como um banco de dados.

Resumindo, conforme afirmado no Scrum Guide, qualquer trabalho que é necessário para melhorar o produto pode ser incluído no backlog do produto.

O que não pode faltar
  • Correção de bugs (sobretudo importantes/demorados)
  • Manutenções adaptativas (ex.: migrar framework, banco ou linguagem)
  • Refatorações grandes / pagamento de débito técnico
  • Instalação ou configuração de sistema/framework complexo
  • Síntese (Scrum Guide): qualquer trabalho necessário para melhorar o produto
Matéria por trás da questão

U4 · Scrum — backlog e planejamento

  • Backlog do produto: lista de histórias, priorizada (topo = maior prioridade) e dinâmica (histórias entram e saem).
  • Planejamento do sprint — 1ª parte: definem-se as histórias do sprint. 2ª parte: histórias viram tarefas alocadas a devs (backlog do sprint).

Qual a diferença entre as histórias do topo e do fundo do backlog do produto?

Resposta Gabarito do professor

Histórias do topo do backlog do produto são menores, têm uma estimativa de tamanho mais precisa e maior prioridade. As histórias do fundo são maiores e mais vagas, isto é, não possuem uma especificação e estimativa de tamanho confiáveis.

Histórias do topo do backlog: maior prioridade, mais claras e bem definidas, menores.
Histórias do fundo do backlog: o contrário

O que não pode faltar
  • Topo: maior prioridade
  • Topo: menores, mais claras e bem definidas
  • Topo: estimativa de tamanho mais precisa
  • Fundo: maiores e mais vagas
  • Fundo: sem especificação e estimativa confiáveis

Suponha dois times, A e B, atuando em projetos diferentes, contratados por empresas distintas:

  • Ambos adotam sprints de 15 dias
  • Ambos possuem 5 devs
  • O time A considera que sua velocidade é de 24 pontos
  • Já o time B possui uma velocidade de 16 pontos

Pode-se afirmar que A é 50% mais produtivo que B? Justifique sua resposta.

Resposta Gabarito do professor

Não, pois story points é uma medida totalmente interna de cada time. Por exemplo, uma determinada história pode ter 6 story points para um time e 4 story points para outro time (exatamente a mesma história).

O que não pode faltar
  • Resposta: Não
  • Story points são medida interna de cada time
  • Não são comparáveis entre times diferentes
  • Exemplo: mesma história com pontos diferentes em cada time
Matéria por trás da questão

U4 · Scrum — DoD e Story Points

  • Definition of Done (DoD): critérios internos para considerar a história pronta.
  • Exemplos de DoD: testes de unidade com cobertura ≥ 75%, revisão de código por outro dev, atualizar documentação se a API mudou, teste de performance.
  • Story Points: estimam o TAMANHO das histórias e ajudam a definir o que cabe no sprint. Uso não é obrigatório; definição é empírica.
  • Escala mais comum: 1, 2, 3, 5, 8, 13… (Fibonacci).
  • Velocidade: número de story points que o time consegue implementar em um sprint.

📌 Kanban · Q12 a 14 · 1 questão na prova antiga

Na prova antiga caiu um caso de violação do limite WIP: a resposta é a da 12 (limite WIP evita sobrecarga, "pare de começar e comece a terminar"). A 14 é a mesma ideia vista do outro lado.

Pergunta Caiu na prova antiga
12enunciado completo da Lista 1

Um dos problemas comuns em times de software é o excesso de trabalho. Como Kanban pode ajudar a resolver esse problema?

Resposta Gabarito do professor

Definindo um limite WIP para cada coluna do quadro.

O que não pode faltar
  • Cita limite WIP (Work in Progress)
  • Limite definido para cada coluna/passo do quadro
  • Relaciona o limite a evitar sobrecarga do time
Matéria por trás da questão

U4 · Kanban

  • Origem nos anos 50 no Japão, Sistema de Produção da Toyota (manufatura lean, just-in-time). kanban = 'cartão visual'.
  • Colunas típicas: Backlog → Especificação → Implementação → Revisão de Código, cada uma com sub-colunas 'em andamento' e 'concluídas'.
  • Limites WIP (Work in Progress): número máximo de tarefas em um passo, contando em andamento + concluídas.
  • Objetivos do WIP: criar fluxo sustentável, evitar sobrecarga do time e evitar concentração de trabalho em um passo. WIP é um 'acordo' entre time e organização.
  • Frase-síntese: 'pare de começar e comece a terminar'.

U4 · Kanban vs Scrum (comparação direta)

  • Kanban é mais simples; não existem sprints.
  • Não é obrigatório usar papéis e eventos — incluindo Scrum Master, daily, retrospectivas e revisões.
  • Membros 'puxam' o trabalho: escolhem uma tarefa e a concluem.
  • Kanban é mais adequado a times maduros; sugestão comum é começar com Scrum e depois migrar.
  • Kanban é evolucionário: começa com o que se faz hoje, entende o fluxo e os gargalos, e implementa melhorias graduais.

🗂️ Gerência de projetos e PMBOK · Q20 a 27 · 1 questão em 2 parágrafos na prova antiga

Na prova antiga: parágrafo 1 = estruturas organizacionais (23), parágrafo 2 = áreas de conhecimento do PMBOK (24). Estude a 25 e 26 junto: integração e TAP.

Pergunta Caiu na prova antiga
23enunciado completo da Lista 1

O gráfico abaixo representa as influências organizacionais no gerenciamento de projetos. Explique esse gráfico, incluindo nessa explicação uma breve definição do que são as estruturas organizacionais Funcional, Matricial Fraca, Matricial Balanceada, Matricial Forte e Projetizada.

Resposta Gabarito do professor

O gráfico representa os 5 tipos comuns de estruturas organizacionais, destacando que eixo X que uma estrutura projetizada em uma empresa dá mais liberdade e autoridade aos gerentes de projetos, já que nesses casos a empresa funciona por projetos e não por departamentos ou estruturas físicas e rígidas. O inverso ocorre no eixo Y, onde a autoridade do gerente funcional é maior em empresas que adotam uma estrutura funcional ou matricial. A explicação por isso e de cada estrutura segue abaixo:

Estrutura Funcional: O essencial é a hierarquia. A alocação dos membros da equipe é por especialidade, ex.: TI, MKT, ENG. E os mesmos possuem um superior direto. Os especialistas dividem o seu tempo em atividades do departamento e do projeto.

Estrutura Matricial Fraca: Na Estrutura Matricial Fraca não existe a figura do Gerente de Projeto e sim do líder de projeto ou coordenador de Projetos; O Coordenador de Projetos possui pouca ou quase nenhuma independência e autoridade. A função principal do GP é de auxiliar e coordenar as comunicações, com algum nível de autoridade e tomada de decisões, sendo subordinado à um superior de nível mais alto.

Estrutura Matricial Balanceada: Reconhece a necessidade de um gerente de projetos, mas não fornece a ele autoridade total sobre o projeto e seus recursos financeiros. O GP está 100% dedicado ao projeto. O poder é compartilhado entre GP e o gerente funcional.

Estrutura Matricial Forte: As matrizes fortes possuem muitas características da organização por projeto; Podem ter gerentes de projetos em tempo integral com autoridade considerável e pessoal administrativo em tempo integral. O GP está 100% dedicado ao projeto. Possui uma equipe específica e totalmente dedicada ao projeto.

Estrutura Projetizada: Os membros da equipe geralmente são colocados juntos e se reportam diretamente ao gerente de projetos; Os gerentes de projetos possuem grande independência e autoridade; Os departamentos reportam ou prestam serviços (subprojetos) aos diversos projetos. A equipe do projeto está 100% dedicada ao projeto.

O que não pode faltar
  • Eixo X (autoridade do GP) cresce rumo à projetizada; eixo Y (funcional) o inverso
  • Funcional: hierarquia, equipe por especialidade, tempo dividido
  • Matricial Fraca: coordenador/líder com pouca autoridade
  • Balanceada: GP 100% dedicado, poder compartilhado com o gerente funcional
  • Matricial Forte: GP em tempo integral, autoridade considerável, equipe dedicada
  • Projetizada: equipe reporta ao GP, grande autoridade, 100% dedicada
Matéria por trás da questão

U3 · Estruturas organizacionais (1/2)

  • FUNCIONAL — hierarquia é o essencial; equipe por especialidade; GP praticamente inexistente. Vantagem: especialização. Desvantagem: sem visão clara do projeto, burocracia entre departamentos.
  • MATRICIAL FRACA — não há GP, e sim coordenador/líder; pouca autoridade; não dedicado 100%.
  • MATRICIAL BALANCEADA — reconhece o GP, mas sem autoridade total sobre recursos financeiros; poder compartilhado com o gerente funcional.

U3 · Estruturas organizacionais (2/2)

  • MATRICIAL FORTE — GP em tempo integral, autoridade considerável, equipe dedicada.
  • PROJETIZADA — GP com autoridade e autonomia 100%; equipe 100% dedicada. Desvantagem: duplicação de recursos e instabilidade no encerramento.
  • A autoridade do GP cresce de Funcional → Projetizada.

O que é um projeto de software?

Resposta Gabarito do professor

Um empreendimento não repetitivo, caracterizado por uma sequencia clara e lógica de eventos, com início, meio e fim, que se destina ao desenvolvimento de um software, sendo conduzido por pessoas dentro de parâmetros predefinidos de tempo, custo, recursos envolvidos e qualidade.

O que não pode faltar
  • Empreendimento não repetitivo
  • Sequência clara e lógica de eventos
  • Com início, meio e fim
  • Destina-se ao desenvolvimento de um software, conduzido por pessoas
  • Parâmetros predefinidos de tempo, custo, recursos e qualidade
Matéria por trás da questão

U3 · O que é um projeto

  • Projeto: esforço temporário empreendido para criar um produto, serviço ou resultado exclusivo (PMBOK).
  • Características: temporário (início e fim definidos), entregas exclusivas, elaboração progressiva.
  • Fim do projeto: objetivos alcançados; objetivos não poderão ser alcançados; ou a necessidade estratégica deixou de existir.
  • Etimologia: PROJECTUM, 'algo lançado à frente' (PRO = à frente + JACERE = lançar).
  • Elementos repetitivos não retiram a unicidade (ex.: condomínio com prédios de mesma arquitetura).

U3 · Projeto vs Processo (cai muito)

  • PROJETOS: temporários e exclusivos → incertezas. Resultados únicos, elaboração progressiva, fim previsível.
  • PROCESSOS: contínuos e repetitivos → certezas. Atividade repetitiva, permanente, resultados padronizados.
  • Operação/atividade = procedimentos rotineiros, padrões pré-estabelecidos, sem planejamento específico em cada caso.
  • Exemplos de NÃO-projeto: manutenção periódica de equipamentos, manutenção corretiva, backup e rotinas de servidores, help desk, atualizar versão de app em desktops.
  • 'A visão de futuro de uma empresa só pode ser alcançada por meio de Projetos.'

Dica: O professor deu dois cenários para classificar. Treine: instalar software homologado para 1 usuário = NÃO é projeto; atualizar SGBD em 10 países em 6 meses = É projeto.

U1 · O que é Engenharia de Software

  • Engenharia de Software = resolver problemas do mundo real por meio de software.
  • Software (IEEE 610.12-1990): conjunto de programas, procedimentos, documentação associada e dados relacionados à operação de um sistema.
  • Engenharia de Software: aplicar métodos científicos ou empíricos para criar, melhorar e implementar software.
  • O termo 'software' foi cunhado por John Tukey em 1958.
  • O termo 'software engineering' foi consagrado na conferência da OTAN na Alemanha, em 1968.

U1 · A crise do software (fim dos anos 60 / início dos 70)

  • Também chamada de 'Software Crisis' ou 'Software Gap'.
  • Sintomas: projetos falhando ou abandonados; atrasos; acima do orçamento; software não confiável e de difícil manutenção; dificuldade de atender aos requisitos do cliente.
  • Causas: computadores mais potentes e linguagens mais robustas; crescimento da demanda; software mais complexo; mais pessoas envolvidas.
  • Causas (lado humano): formação de profissionais, metodologias, comunicação com clientes, trabalho em equipe.

Descreva pelo menos 2 exemplos de sistemas/softwares em que metodologias de processo de software tradicionais, como o modelo em cascata, são adequadas.

U4 · Os modelos de processo

  • Codifica-Remenda: modelo sem plano algum.
  • Cascata: primeiros modelos dirigidos a planos — Requisitos → Análise → Design → Implementação → Testes.
  • Desenvolvimento Incremental: especificação, desenvolvimento e validação intercalados; pode ser dirigido a planos ou ágil.

U4 · Por que o Cascata falha em software

  • A divisão inflexível em estágios distintos dificulta responder a mudanças de requisitos.
  • Uma fase precisa terminar antes da próxima começar.
  • Só é apropriado quando os requisitos são bem entendidos e as mudanças serão limitadas — e poucos sistemas de negócio têm requisitos estáveis.
  • Engenharia tradicional (civil, mecânica) trabalha com big upfront design e sequencial; software é abstrato e 'adaptável', logo é diferente.
  • Clientes não sabem exatamente o que querem; funcionalidades são 'infinitas' e o mundo muda. Se levar 3 anos, o software nasce obsoleto.

Matéria por trás da questão

U4 · Lidando com mudanças

  • Prevenção de mudanças: o processo antecipa possíveis mudanças antes que o retrabalho seja necessário (ex.: prototipação).
  • Tolerância a mudanças: o processo acomoda mudanças a custo relativamente baixo — geralmente via desenvolvimento incremental.
  • Mudanças são inevitáveis: mudam o negócio, surgem novas tecnologias, mudam plataformas.
  • Mudança gera retrabalho: o custo inclui reanálise de requisitos + implementação das novas funções.

U4 · Manifesto Ágil (2001)

  • Ideia central: desenvolvimento ITERATIVO, em vez do fluxo único do Waterfall.
  • Ciclos curtos geram aprendizado entre devs e clientes e entregam valor (resolver problemas usando software) continuamente.
  • Métodos estudados na disciplina: Extreme Programming (XP), Scrum e Kanban.
